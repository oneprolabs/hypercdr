# Current cluster registration

The Clusters management page and protection wizard share registration UI. Native Kubernetes, Huawei CCE and OpenShift expose Install for me and Run command paths. Registration persists cluster/session state; the caller refreshes its resources after success.

Both paths need a kubeconfig with sufficient Kubernetes permissions. Install for me uploads it to the registration session and delegates installation to the internal registration executor; the executor must reach the API endpoint. Run command uses the platform-generated installer on a host that can reach the cluster API and platform. Run the single installation command as the Linux user whose cluster access is configured. The scripts use that user’s `KUBECONFIG` (including merged files) or `~/.kube/config`; no export, dedicated directory, or root shell is required. If no configuration is found, an interactive prompt asks for a kubeconfig path. The installation script checks access and asks for target confirmation before changing the cluster. Do not invent a token or reuse another cluster's command.

The command contains the registration token, platform endpoint, cluster type, namespace and executor options. Treat it and kubeconfig as credentials. Native/CCE and OpenShift have separate component paths, selected from the active release manifest; a successful platform installation alone does not prove all component images are reachable from cluster nodes.

Completion requires a connected agent and reported inventory, not merely copying a command. Check the cluster card status and agent namespace pods. Use the cluster card's unregister action for standard removal. Removing pods alone does not perform platform unregister; deleting only platform records does not prove cluster resources were cleaned up. For disconnected clusters, consult [offline cleanup](../agent-offline-uninstall.md).

Implementation: `frontend/src/features/clusters/`, `backend/internal/httpserver/`, `scripts/agent/`, and the cluster registration executor image. See [first use](../user-guide/first-use.zh.md) and [troubleshooting](../operations/troubleshooting.zh.md).

## Command-path access check

The public `/check-cluster.sh` asset is independent of release component images and contains no tokens or user credentials. This optional diagnostic asset is not a separate UI step. The UI shows environment prerequisites followed by a single installation command for the selected provider. Run it from a Linux administration host with bash, curl and kubectl, access to the platform and target API, and cluster administrator credentials. OpenShift users first complete `oc login`; CCE users without a configured client download their cluster-admin kubeconfig and upload it to the execution host.

The shared checker prints the context, API endpoint and kubeconfig credential-entry name (not a claim about the server-authenticated identity). It verifies namespace access and wildcard cluster administrator authorization with bounded API requests, additionally checks the OpenShift API for OpenShift, and reads target confirmation from `/dev/tty` so piped execution works. It does not change cluster resources or kubeconfig, install dependencies, or upload credentials. Declining confirmation stops the command. A successful access check does not certify storage, image pulls or complete provider compatibility; existing installer checks still apply.

The installation command runs the shared selection and access-check functions and asks for target confirmation before cluster changes. Internal platform-direct jobs supply their temporary kubeconfig and context and run the checks noninteractively; interactive confirmation is not added to those jobs. Native/CCE continue using `hypercdr-agent`, and OpenShift continues using `openshift-adp`.
