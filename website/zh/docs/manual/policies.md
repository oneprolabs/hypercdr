# 保护策略

入口：**Configuration → Policies**。

策略回答两个问题：**什么时候备**，**备完留多久**。它本身不绑定具体应用——绑定动作在[应用容灾保护](/docs/manual/application-dr)里完成，所以一个策略可以被多个应用引用。

## 策略包含什么

| 部分 | 作用 |
| --- | --- |
| 保护计划 | 备份的执行节奏 |
| 保留规则 | 恢复点留存的时间或份数 |
| 作用范围 | 策略应用时保护的资源范围 |

创建入口有两个：Policies 管理页直接新建，或在保护向导里顺带创建。两处复用同一套创建界面。

## 保留规则要算清楚

保留规则直接决定存储占用。估算方式：

```text
需要的存储 ≈ 单次备份大小 × 每个应用的保留份数 × 应用数量 × 增长系数
```

几个容易踩的点：

- 保留份数按**恢复点**算，不是按天算。一天备两次，保留 7 份只能覆盖三天半。
- 多个应用共用一个存储时，容量是累加的。
- 演练和恢复也会临时占用恢复缓存（见[Velero 恢复缓存](/docs/operations/restore-cache)），容量规划要留余量。

::: warning 过期清理是正常的

恢复点数量不增长，不一定是备份失败，也可能是保留规则在清理旧恢复点。核对任务记录再下结论。

:::

## 修改策略的影响

- 缩短保留期会加速旧恢复点被清理，**已经删掉的恢复点无法找回**。
- 放宽备份频率会增加存储和网络压力，先确认容量。
- 修改策略后，已产生的恢复点按新规则处理，不会追溯重建。

建议在变更前记录当前保留规则和恢复点数量，变更后观察一两个周期再继续调整。

## 策略与应用的关系

```text
策略 A ──┬── 应用 1（namespace: app-a）
         └── 应用 2（namespace: app-b, app-c）

策略 B ──── 应用 3（namespace: app-d）
```

一个应用在同一目标上应避免同时挂多个策略，否则任务会叠加执行，存储占用和调度压力都会上升。

## 检查清单

- [ ] 保留份数覆盖了业务要求的恢复窗口
- [ ] 存储容量按最坏情况估算过
- [ ] 策略绑定到了预期的应用，没有遗漏或多余
- [ ] 修改保留规则前已确认旧恢复点可以淘汰
