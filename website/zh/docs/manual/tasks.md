# 任务与恢复点

入口：**Backup & Recovery Tasks**（执行记录）和 **Restore Points**（可恢复时间点）。

## 任务与恢复点的关系

```text
保护策略调度 → 产生任务 → 任务成功 → 生成恢复点
                                ↘ 任务失败 → 无恢复点（或部分失败）
```

任务记录"这次执行怎么样"，恢复点记录"能回到哪个时刻"。两者不能互相替代。

## 看任务时看什么

| 字段 | 怎么用 |
| --- | --- |
| 状态 | 区分成功、失败、进行中，失败要看具体阶段 |
| 时间 | 与策略调度时间对比，判断是否延迟 |
| 详情 | 错误信息与执行阶段，定位到存储、Agent 还是资源映射 |
| 日志 | 具体错误堆栈，排查时最有用 |

::: tip 先用任务详情定位，再翻 Agent 日志

任务详情通常已经指出是存储访问、PVC/StorageClass 还是资源映射的问题。直接翻 Agent 日志容易淹没在无关输出里。

:::

## 常见失败类型

| 错误特征 | 含义 | 处理方向 |
| --- | --- | --- |
| 存储访问被拒 | 凭据失效、bucket 权限不足、endpoint 不通 | [对象存储](/docs/manual/storage) |
| PVC / StorageClass 相关 | 目标集群缺少对应存储类，或动态供给失败 | 核对目标集群存储能力 |
| 资源映射冲突 | 目标 namespace 已有同名资源 | 调整恢复目标或映射 |
| `RESTORE_CACHE_PREFLIGHT_FAILED` | 演练前恢复缓存预检未通过 | 见 [Velero 恢复缓存](/docs/operations/restore-cache) |
| Agent 超时 | 集群侧网络或负载问题 | 看集群状态与 Agent 日志 |

## 恢复点

在 **Restore Points** 中确认：

- 恢复点的时间与任务记录对应；
- 恢复点关联的存储与应用正确；
- 保留规则没有把它清理掉。

恢复点数量不增长时，先分清是**任务失败**还是**保留规则在清理**。

## 执行恢复之前

::: danger 恢复会覆盖目标

实际 Recovery 之前必须核对**目标与资源映射**，避免覆盖现有业务。恢复不是无副作用的操作。

:::

建议顺序：

1. 先在[演练](/docs/manual/drill)中验证同一恢复点可用；
2. 确认目标集群、目标 namespace、存储类映射；
3. 确认目标侧同名资源是允许被覆盖的；
4. 执行恢复，并跟踪任务进度；
5. 恢复后校验工作负载、PVC 和应用数据。

## 恢复之后要验证什么

任务成功不代表应用可用。至少检查：

- [ ] 工作负载（Deployment/StatefulSet 等）已就绪，副本数符合预期
- [ ] PVC 已绑定，数据可读
- [ ] 应用能对外提供服务
- [ ] 数据内容与恢复点时间相符
